Its concrete stale-commit counterexample is in `moon-review`. This preserves calculations and existing labels while preventing old input from overwriting current state.
2. **Coverage activation:** add one unknown-time admission step using the reviewed interval API. `empty` is a date-specific rejection; `unresolved` is inability to establish coverage, not a nonexistent date. Never substitute hourly sampling. Validate that the chosen representative instant belongs to an admitted interval; do not silently switch local-noon receipt semantics or invent a replacement time. Known-time calculations, positions imports and saved v1 reconstruction remain separate.
3. **Required compatibility choice:** when native transition enumeration is missing/failing, either reject that unknown-time request with a localized explanation, or explicitly provide an unverified reference-only result. The first narrows existing functionality on those runtimes; the second requires a coherent reference/uncertainty presentation in cards, readings, context and shares. Neither can be decided by treating provider absence as empty or claiming complete coverage from the legacy helper. Missing capability is an observed Node 22 condition; no unverified browser-market support claim is made.
4. **Required certainty choice:** disconnected and long dates can either be rejected temporarily, or admitted as explicit reference-only output with no singular unknown-time Registry bridge and no unsupported whole-date Sun/Moon candidates. A duration cutoff such as 25 hours is a product scope limit, not proof that two astronomical endpoint signs exhaust the date. Retaining existing definitive singleton semantics requires a separate reviewed body-specific event/coverage contract. The safe conservative option uses generic “not established” copy, not “changed signs,” and carries the reason through share/context consumers.

There is no safe drop-in replacement of `localDateEndpointsUtc` that resolves those presentation decisions. The smallest complete activation should choose one of the above compatibility/uncertainty policies and update its consumer boundary atomically, while leaving the numerical interval module unchanged. These are product/compatibility decisions for the accountable integrator, not publication, outreach or spending approvals.
