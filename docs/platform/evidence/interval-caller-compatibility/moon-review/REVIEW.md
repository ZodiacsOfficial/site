## Reproduced controls

The isolated driver extracts the production lookup closure exactly through TypeScript AST and executes it with observable state setters and a controlled loader. Production resolver, lite phase function, pure sign logic and the exact current rc.6 engine bytes run. This is a source-level async calculation control, not a native DOM test or independent astronomical accuracy verification. Extraction line ranges and hashes are recorded.

1. **Missed valid Moon sign:** Toronto 1919-03-31 with unknown time currently displays only Aries. Its first sample is 05:00Z (local 01:00); the real date begins 04:30Z (local 00:30). The engine Moon at that first valid instant is 359.7145003582242° (Pisces). The last member is 14.454372541038538° (Aries). The old gap policy therefore drops a real Pisces part of the requested date. This is a finite counterexample to the existing endpoint result, not a claim that endpoint replacement proves all dates.
2. **Empty date returns another date's result:** Apia 2011-12-30 has no interval. The current lookup nevertheless makes four engine calls at local 2011-12-31 noon/midnight/23:59 and displays Pisces/Aries. All four instants are outside the requested date.
3. **Repeated/disconnected controls:** Apia 1892-07-04 has 48 continuous UTC hours; current 23:59 resolves to the earlier occurrence, dropping the second 24 hours from its sign check. The tested endpoint signs still happen to fit Libra/Scorpio; no missing third sign is claimed. St Johns 2009-11-01 has two intervals separated by an hour of the previous date; a single enclosing range would include nonmembers. Its observed endpoint signs are Aries/Aries and Aries/Taurus, not a whole-date proof.
4. **Stale ownership:** The exact lookup started for 2000-01-01, with engine loading held pending, then completed after the visible input had changed to 2000-06-15. It committed the January result (Moon 223.3238911274741°) instead of the fresh June result (248.9044490599416°). Lookup contains no input identity. A later failed lookup retains the old result beside its error.

The stale mechanism is source-backed: fields remain editable (188–205); input handlers only set values; lookup has no revision token (84–140); catch sets only error, finally always clears busy, and result remains rendered whenever non-null (220). PlaceSearch clears selection on typing/removal (54–57, 111), so city removal must also invalidate a pending request. The shared module loader shares/import-caches code, not per-form result ownership (useEngine.ts:6–15; module-load.ts:19–31). Focus-after-compute is another shared mutable ref and must be fenced on edits.

A small pre-existing copy control also contradicts the date-alone exactness prose: lite moonPhaseName changes within UTC 2024-01-09 from Waning Crescent to New Moon and within 2024-01-16 from Waxing Crescent to First Quarter. The page's FAQ at EN moon-phase/index.astro:32 and reading prose at 111–114, plus ui/en.ts:300, say the phase is unaffected/exact from the date. These are existing product claims; they are not fixed or expanded into the selected ownership slice.
